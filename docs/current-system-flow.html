Current system flow

Puzzle Telemetry Rig, Phase 1 — the live Raspberry Pi dashboard, two ultrasonic sensors, limit switch, webcam, completion check, and session CSV.

Current design, rev 4. This document describes the running dashboard flow. Wiring remains controlled by docs/wiring.md; runtime behaviour is controlled by src/tools/live_dashboard.py.

Both HC-SR04 Echo signals pass through their own 1 kΩ + 2 kΩ voltage divider before reaching the Pi. The camera is USB. The e-paper display is currently disconnected.

2. Session flow

1READYDashboard polls both sonars and waits for a switch press. A sustained nearby reading may create a pending approach.
2START CHECKFirst press takes the current camera frame and checks that the puzzle is not already complete.
3TIMINGFor an incomplete puzzle, record start_ts, attach the pending approach if present, and run the stopwatch. New approaches are paused.
4STOP CHECKEvery later press checks the live camera frame against the saved solved-T reference. It must pass before the deadline.
5DONEOnly a passing reference check before the deadline stops the timer and appends the session row. The next press begins a new start check.
Normal route: first press → puzzle is incomplete → timing starts. Later press → T is complete → save the metrics and finish.
Already solved at first press: the system returns to READY. It does not start the timer and does not create a session row.
Incomplete on a stop press: the timer keeps running. No session row is written; the visitor can continue and press again later.
No successful verification within 5 minutes: the rig saves one row with completed=abandoned, returns to READY, and does not carry an approach into the next session.

4. Edge cases and safeguards

SituationCurrent behaviour
One sensor returns NO ECHOThat reading is ignored. The other sensor can still create an approach event.
Brief pass near the tableNot recorded as an approach unless proximity remains at or below 80 cm for the full 1.0-second hold period.
Approach is not followed by a startIt expires after 60 seconds, so its values will not be attached to a later session.
Person moves away after an approachAfter 10 seconds away from the threshold, the stored approach resets.
Switch bounceGPIO26 uses 50 ms debounce, so ordinary contact bounce should not generate multiple presses.
Start pressed while the T is already solvedTimer remains stopped, no row is written, and the dashboard asks for the puzzle to be reset.
Stop pressed while T is incompleteTimer continues; no incomplete result is saved as a completed session.
Camera check finishes after the 5-minute deadlineThe deadline wins: the session is saved as abandoned, not as a successful solve.
Camera frame unavailable or completion check errorsAt start: return to READY without timing. At stop: keep timing and ask for another check.
CSV write fails after a complete TThe dashboard displays an error; the completed session was not saved and should be investigated before the next visitor.
Both sonars hear each otherThe code triggers and reads them in sequence, rather than pinging both at once, reducing ultrasonic cross-talk.

5. Current limitations to keep in mind

Completion accuracy

The completion decision is a fixed-camera HSV colour, contour-shape, and area comparison. It should be validated with labelled complete and incomplete examples under the final lighting before relying on it for formal measurement.

Configured but not yet active

result_hold_s is reserved for the future e-paper display. The dashboard keeps a result visible until the next switch press; it does not automatically clear after 20 seconds.

6. Configuration that controls the flow

src/config.yaml → session is the source of these values: approach_cm: 80, approach_hold_s: 1.0, approach_reset_s: 10, near_timeout_s: 60, and safety_timeout_s: 300. The T-completion HSV threshold, contour shape threshold, and area-ratio threshold are in the same file under completion.
